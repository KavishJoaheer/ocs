# OCS teleconsultation and operator-led onboarding

Operators create or find the patient in VP. The compact **Send OCS Care link** action in the patient profile opens an on-demand dialog; the invitation form is hidden during normal profile viewing. Choose **Patient records** for general Care access, or **Teleconsultation** to also record hotline screening. Both require identity and personal-mobile confirmation; the teleconsultation option also requires the screening checkbox. Create the personal invitation and copy it into the confirmed patient's WhatsApp conversation. Closing the dialog clears its local invitation and confirmations. No WhatsApp message or call is sent automatically.

Generated invitations display the URL in its own selectable field, with the message and expiry details underneath. **Copy invitation for WhatsApp** copies the URL first, a blank line, then the patient instructions. **Copy link only** copies just the URL.

The patient follows the link and presses **Continue to OCS Care**. No email address or password is required for an invited account. The normal dashboard contains **Request a teleconsultation**. The patient supplies the reason, current location and confirmed callback number, reads the terms and limitations, and accepts both the terms and clinical consent. A six-digit consultation code is then visible to the patient and operator.

On mobile, the dashboard card is a single large tap target. Requesting has two steps: **Your details**, then **Review & consent**. The verified callback number is prefilled and read-only; changes go through OCS. Returning to edit retains the entered details. The confirmation view shows request sent, OCS accepted and doctor assigned, with the consultation code clearly separated. A dependent's request remains hotline-assisted.

New requests create a persistent, non-dismissable in-app alert across VP pages for operators and administrators. It is fetched from saved server state, oldest first, independently of the management history limit. Viewing a request, navigating away or reloading does not acknowledge it. **Accept** records the staff member and timestamp; only then can dispatch assign a doctor. A shared acceptance removes the alert for all operators, while cancellation also removes it. Concurrent attempts preserve the first acceptor; failed actions keep the request visible. Alerts refresh through realtime events, with a ten-second polling fallback. Native push uses a distinct request tag; device permission and operating-system notification behaviour still apply.

VP and Care mobile text-entry controls use a 16px font to avoid iOS focus auto-zoom, without restricting pinch zoom. Bottom navigation hides while an editable text field is focused and returns on blur, leaving more space for writing.

The same text-entry treatment applies to Android, including Samsung Internet and Huawei Browser. Focus handling uses standard DOM events rather than newer CSS selectors, including for modal forms. Care's shared theme adds deep teal page headers, gold accents, stronger navigation selection and tinted card surfaces across the dashboard, records, visits, stories and profile. Consultation status, the assigned doctor and the copyable appointment code have separate visual areas; clinical text and editable fields retain readable light backgrounds.

Future sign-in setup is offered only when a patient without a password taps **Sign Out**, in the profile or desktop sidebar. **Set up future sign-in** lets them choose an email and password, confirm the password, and **Save & sign out**. The login screen explains that these are their credentials and prefills only the email. **Sign out for now** skips setup and explains that OCS must issue a new personal link for their next visit. **Stay signed in** cancels. Existing password users sign out normally, without this prompt.

The VP **Manage teleconsultations** section in the main navigation lets dispatch assign an active doctor across all patient requests. It is separate from the patient-specific invitation dialog. The page opens with active requests, status counts, patient/mobile/reason search and status filters. Expand one request at a time; folding, filtering and background refresh preserve entered notes while the page stays open. Completing a request keeps it open in the completed view.

The assigned doctor contacts the patient using WhatsApp, confirms identity, location, privacy, consent and suitability, and verifies the appointment code. The consultation form requires **Consultation note (not visible to patient)** and **Patient-facing diagnosis / assessment**. **Prescription (optional)** and **Patient care summary (optional)** can be left empty. There is no follow-up field in the completion form. Private and patient-visible fields are visually separated. Completion creates the existing consultation and billing records; patients access the diagnosis and any prescription or summary through Care. Internal clinical notes are not included in patient responses. Existing follow-up data remains readable, and a separate referral/cancellation action records a patient-facing reason and next step.

All active requests remain in the management view regardless of volume; only closed history is limited to the latest 100. Editing a saved structured consultation uses separate private-note, diagnosis and prescription fields in both staff editors. Amendments update Care and reuse the existing bill. A blank optional prescription stays blank and is never inferred from the private note. The care summary is also included in the permanent health record, and prescription display and export preserve the doctor's full patient-facing text. Voided records disappear from patient records, visits and dashboard while staff retain the audit record.

Care refetches on realtime connection, return to the app and network restoration, including updates missed while disconnected. Obsolete streams cannot reopen after sign-out or an account switch. Temporary sign-in failures allow retrying the same unconsumed invitation. Health-record refreshes keep an expanded record visible; failures clearly mark the last loaded information. Referral/cancellation next steps remain visible on the request screen.

## Configuration

Production invitations default to the established Care origin, `https://ocsvp.com`, including on existing NAS deployments without a `PATIENT_PORTAL_ORIGIN` setting. Both Compose files also supply this default. Set `PATIENT_PORTAL_ORIGIN` explicitly only if the public Care domain differs. An override must be an HTTPS origin without a path, credentials, query or fragment. The resolver never uses the staff portal's `CLIENT_ORIGIN` or request headers. Development defaults to `http://localhost:5174`. The patient portal and API must use the existing credentialed cookie arrangement.

Review the versioned patient terms in `server/src/lib/teleconsultations.js` with the OCS clinical lead before offering the service. They disclose WhatsApp, remote-assessment limitations, emergency exclusions, connection failure, patient choice and fee confirmation. They do not set a new fee or guarantee a response time. Existing billing creates a fee-review-required bill unless an existing consultation category is explicitly supplied. The workflow does not add call recording or ID-image storage.

## Access controls and lifecycle

- Magic links expire 10 minutes after issuance and are single-use. Replacement invalidates earlier unused invitations. Expiry does not end an authenticated session or consultation.
- Tokens are 32 random bytes encoded as 43 URL-safe characters; previously issued 64-character hexadecimal tokens remain valid until used or expired. Only their hashes are stored. URL fragments keep raw tokens out of HTTP request URLs. Care removes the fragment from browser history and consumes the token only on the patient's explicit action, not a preview GET.
- Redeeming the link creates a normal HttpOnly cookie session. Invited accounts have null email/password fields; no default passwords or invented addresses are created. Existing email/password accounts remain supported.
- Future sign-in setup requires an authenticated, clinic-confirmed account without a password. It updates the existing account without creating another patient record, checks email uniqueness without regard to case, and hashes the chosen password. Saving atomically revokes all prior sessions, reset tokens and unused invitations, then clears the cookie. Validation or save failures preserve access; failed sign-out requests leave the patient signed in with a retry message.
- Invitations require identity and mobile confirmation. Pending ownership, inactive accounts, conflicting account/mobile associations, dependents, changed mobile numbers and disabled issuers cannot bypass checks. A new account is created only on successful redemption.
- Staff may record teleconsultation screening while creating the invitation. Patient requests require screening within the last 24 hours on the same confirmed mobile. Dependent consultations remain a hotline-assisted process.
- Consent version, full wording and patient acceptance time are stored per request. No active request or consultation code is created before patient consent. Operator acceptance is recorded separately before doctor assignment. One active request per patient is enforced in the database.
- Doctors see only their assigned queue. Starting a consultation requires the appointment code and confirmed clinical checks; five incorrect attempts block further starts until dispatch reviews/reassigns the case. Clinical completion is restricted to the assigned doctor or administrator.
- Completion, cancellation and referral remove the code from API responses. Prescription and patient-summary content is separate from the internal clinical note.
- Purging patients removes invitation and teleconsultation data. Merging patients revokes invitations and clears screening; merging two active teleconsultations is blocked until one is resolved.

## Verification

`server/tests/teleconsultations.test.js` covers onboarding, token hashing/expiry/replay/replacement, account ownership, role restrictions, consent, code verification, referral and record visibility, plus migration preservation of sessions and foreign keys. Acceptance checks include competing operators, idempotent retry, assignment gating, cancelled requests, one-time migration, and alerts beyond the history limit. It also checks future credentials, duplicate-email rejection, failed-setup access preservation, session and link revocation, and return access to the same patient record. `e2e/teleconsultation.spec.js` walks through the operator, mobile patient and doctor screens, including persistent alerts, failed acceptance, two-step consent, retained details and mobile navigation during typing. `e2e/mobile-typing.spec.js` checks input size and focus/blur scale without disabling pinch zoom. `e2e/future-sign-in.spec.js` covers mobile setup, password sign-in, desktop skip, cancel/focus restoration and failed-request recovery.
